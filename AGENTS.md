# Правила работы с Featurify

Инструкции действуют для всего репозитория. Перед изменениями изучи сборку,
ближайший существующий код и соответствующий раздел README. Более конкретные
инструкции вложенного AGENTS.md дополняют эти правила в своей директории.

## Проект и границы модулей

Featurify — сервис feature toggles с изоляцией по namespace, REST/gRPC API
и административным Vaadin UI. Сборка — Gradle Kotlin DSL, toolchain — JDK 25.
Актуальные версии зависимостей смотри в Gradle-файлах и gradle.properties.

- `featurify-api`: Kotlin REST DTO, общие enum и Jakarta Validation.
- `featurify-service`: Kotlin, Spring Boot, REST/gRPC-сервер, Vaadin,
  безопасность, Spring Data JDBC, PostgreSQL и Flyway.
- `featurify-grpc-api`: protobuf-контракт и генерируемые Java-классы.
- `featurify-grpc-client`: Java-клиент без Spring.
- `featurify-grpc-starter`: Java-автоконфигурация для Spring Boot 2, 3 и 4.
- `featurify-demo`: демонстрационное приложение и HTTP-диагностика клиента.
- `compatibility-tests`: отдельная Gradle-сборка для проверки опубликованных
  клиентских JAR в независимых приложениях.

Production-код клиентских gRPC-модулей должен оставаться на Java и совместимым
с Java 8 (`--release 8`). Kotlin в их тестах допустим. Не добавляй в клиентские
артефакты Kotlin runtime, серверные модули, REST DTO, Jakarta Validation, Vaadin
или JDBC. Сохраняй цепочку зависимостей starter → client → grpc-api.
Не создавай новых файлов миграции, вноси изменения по БД (если имеются) в существующую миграцию `V1__create_feature_toggle_schema.sql`.

## Стиль Kotlin и ktlint

- Для Kotlin-кода и `.gradle.kts` придерживайся Kotlin Coding Conventions
  и правил подключённого Gradle-плагина ktlint. При наличии `.editorconfig`
  учитывай его настройки. Не вводи параллельный конфликтующий стиль.
- Используй 4 пробела для отступов, без табуляции и завершающих пробелов.
  Переносы строк, trailing commas и порядок импортов доверяй ktlint.
  Не используй wildcard imports и необязательные точки с запятой.
- Имена классов и интерфейсов — PascalCase, функций и свойств — camelCase,
  констант — UPPER_SNAKE_CASE, пакетов — в нижнем регистре.
  Предпочитай содержательные имена и файл с именем основного класса.
- Пиши идиоматичный Kotlin: `val` по умолчанию, минимальная изменяемость,
  `data class` для объектов данных, выражения `when` и `if`, когда они упрощают код.
  Не переноси в Kotlin Java-паттерны с ручными getter/setter без необходимости.
- Моделируй отсутствие значения через nullable-типы. Предпочитай safe calls,
  Elvis и ранний выход; не добавляй `!!` без обоснованного инварианта.
  Не подменяй некорректные данные молчаливыми значениями по умолчанию.
- Задавай явные типы публичных контрактов. Ограничивай видимость реализаций.
  Не усложняй чтение вложенными scope-функциями и длинными цепочками операций.
- Используй constructor injection и `private val` для зависимостей Spring.
  Для Bean Validation указывай корректный annotation use-site target
  (например, `@field:NotNull`), согласованный с существующими DTO.
- Комментарии объясняют причины и ограничения. KDoc нужен для нетривиальных
  публичных контрактов; не дублируй очевидное поведение кода.
- Не отключай правила ktlint, не добавляй широкие suppression и не меняй
  конфигурацию линтера ради обхода ошибок. Форматирование посторонних файлов
  не включай в функциональные изменения.
- Старайся придерживаться принципа class-per-file. На один файл должен быть один класс (в пределах разумного).

В Java-коде сохраняй существующий стиль, nullability-контракты и ограничения
Java 8. Не используй API или синтаксис более новых Java в клиентских библиотеках.

## Архитектура и контракты

- Контроллеры, gRPC-обработчики и Vaadin views отвечают за транспорт и UI;
  бизнес-правила размещай в сервисах, доступ к данным — в репозиториях.
  Сохраняй транзакционные границы, optimistic locking по `version` и аудит.
- Все операции с данными должны учитывать namespace. Не допускай доступа
  к чужим namespace через ключи фич, групп, идентификаторы или batch-запросы.
- Не смешивай namespace-токены публичного REST/gRPC и административную
  авторизацию Keycloak. Не логируй токены, пароли и client secrets.
- Сохраняй правила BOOLEAN/ENUM/VECTOR, неизменяемость типа фичи, ограничения
  ключей, защиту системного namespace `default` и согласованность каскадных операций.
- Сервис читает актуальное состояние PostgreSQL без кеша конфигурации.
  Не добавляй серверное кеширование без явного требования; клиентский кеш
  имеет отдельные контракты и настройки.
- REST-ошибки должны сохранять существующий формат `application/problem+json`.
  Для gRPC сохраняй осмысленное соответствие ошибок status codes.
- Сохраняй совместимость публичных DTO, protobuf и клиентского API.
  Не переиспользуй номера удалённых protobuf-полей; резервируй их имена и номера.
  Генерируемые классы не редактируй: меняй `.proto` в `featurify-grpc-api`.
- Изменения схемы выполняй через Flyway. По умолчанию добавляй новую миграцию,
  не переписывая уже применённые. Существующая MVP-миграция V1 рассчитана
  на новую базу; её переработка требует явно заданного сценария пересоздания.
  Не удаляй данные или Docker volumes ради прохождения проверок.

## Проверки перед завершением

Используй Gradle Wrapper из корня проекта. Ниже команды для PowerShell;
на Linux/macOS замени `.\gradlew.bat` на `./gradlew`.

```powershell
# Проверка стиля Kotlin и Gradle Kotlin DSL
.\gradlew.bat ktlintCheck

# Форматирование затронутого модуля (пример)
.\gradlew.bat :featurify-service:ktlintFormat

# Тесты затронутого модуля (пример)
.\gradlew.bat :featurify-service:test

# Общая проверка, включая тесты и ktlint подпроектов
.\gradlew.bat check

# Совместимость клиентских артефактов; нужны JDK 8, 21 и 25
.\gradlew.bat verifyClientCompatibility
```

- После форматирования проверь diff: задача модуля может изменить файлы
  за пределами текущей правки. Сохраняй чужие незакоммиченные изменения.
- Для изменений поведения добавляй или обновляй содержательные тесты:
  успешный сценарий, ошибки и существенные граничные случаи. Используй
  существующий стек JUnit 5, AssertJ и MockK/SpringMockK там, где он подключён.
- При изменениях авторизации проверяй изоляцию namespace и отказ в доступе;
  при изменениях записи — конфликт версий, транзакционность и аудит.
- PostgreSQL-тесты включаются через `FEATURIFY_DB_TESTS=true` и требуют
  отдельной тестовой БД с `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`.
  Обычный успешный `test` не означает, что эти проверки выполнялись.
- При изменениях клиентского API, protobuf, зависимостей или автоконфигурации
  выполняй `verifyClientCompatibility` дополнительно к обычным тестам.
- Для правок только документации достаточно проверить содержание и diff;
  запускать сборку без необходимости не требуется.
- Если проверка недоступна из-за окружения, укажи, что именно не выполнено
  и почему. Не выдавай пропущенные проверки за успешные.

## Объём изменений и результат

- Делай минимальные изменения, решающие задачу. Не добавляй зависимости,
  абстракции и несвязанные рефакторинги без практической необходимости.
- Не редактируй вручную build outputs, generated sources и Gradle caches.
- При изменении API, архитектуры или конфигурации соответствующий README и всю необходимую документацию в папке docs. 
  Идентификаторы кода сохраняй на английском, документацию — в языке соответствующего файла.
- В результате кратко опиши, что изменено, какие проверки выполнены
  и какие ограничения остались.
